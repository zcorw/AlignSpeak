已核实，不再反问你的事实

这些是代码和 iOS 平台给出的约束，不属于产品偏好。

现状是段落级 Web 播放

当前只用一个 HTMLAudioElement 播放当前段落的 Blob URL；无下一段、文章队列或循环。

页面离开即停止

播放器属于练习页 Hook；切段会停止，页面卸载会撤销 Blob URL，没有应用级播放生命周期。

没有 PWA 或 iOS 原生壳

仓库目前仅有 Vite/React Web 与 FastAPI，未配置 Manifest、Service Worker、Capacitor 或 Xcode 工程。

Safari 不能承诺可靠后台队列

单个已开始媒体可能锁屏续播，但后台 JS、换段回调、网络续取与锁屏控制不能作为可靠产品能力。

后端只有按段 TTS

已有 MP3 缓存键为段落 + 音色 + 语速 + 文本哈希；没有文章级播放清单、合并音频或持久任务队列。

现有媒体依赖 Bearer 下载

前端先鉴权下载完整 Blob 再播放；这不适合作为长时后台、进程重启或永久离线的主方案。

❓ Q2 - 后台播放的验收边界

首版必须通过哪一级真实场景？这里决定我们是否需要系统音频会话、锁屏元数据和远程控制，而不只是让音频偶尔继续响。

➡️ 推荐 A：用户对“iOS 后台播放”的自然预期就是锁屏、熄屏、切 App 都不中断，并能从系统界面暂停。

❓ Q3 - 一次循环的范围与边界停顿

“文章循环”按什么单位验收？现有文章由多个段落组成；段落间和文章末尾回到开头的停顿标准会决定是播放队列还是整篇单媒体。

➡️ 推荐 A：明确而自然的学习节奏比技术上的零间隙更有价值，也能继续复用现有段落级 TTS 缓存。

❓ Q4 - 首次播放等待与后台准备策略

一篇冷缓存文章可能要生成多个段落。用户第一次点击时，是尽快听到第一段，还是必须等整篇准备完成才允许进入可靠后台循环？

➡️ 推荐 A：先准备一个小缓冲窗口再播放，同时继续下载整篇；既不让用户等完整文章，也避免马上遇到空队列。

❓ Q5 - 断网、登录过期与离线边界

音频已经开始后，如果网络断开或登录 Token 过期，播放必须达到哪一级？是否还要在关闭并重开 App 后继续离线使用？

➡️ 推荐 A：把本次播放需要的媒体写入临时本地缓存，保证会话连续；不要在首版同时承担完整离线下载产品。

❓ Q17 - 播放中启动朗读录音时怎么处理？

最终规划 · 已确认实施基线

设计树已遍历并确认完毕。以下方案由全部 29 项决策共同收敛而成。

1 / 1 已确认
规划状态：已确认并冻结。此状态只授权将方案作为实施基线，并不代表已经开始编码、迁移数据库或修改部署。

1. 产品承诺

  • 正式支持发布时最新稳定版 iOS Safari。
  • Chrome iOS 通过真机核心用例后标记“兼容”，不共享 Safari SLA。
  • 普通 Safari 是主入口；主屏幕 PWA 仅做兼容验证。
  • 锁屏、熄屏、切 App 与系统播放/暂停均为尽力优化，不承诺原生级可靠后台。

2. 播放体验

  • 整篇文章全部段落按顺序循环。
  • 段间停顿 0.5–1 秒，全文循环边界停顿 1–2 秒。
  • 整篇音档准备并完整下载后才允许播放。
  • 首版只提供播放/暂停与循环状态；固定 1.0 倍速、默认音色。
  • 默认无限循环；支持本轮结束、15/30/60 分钟睡眠停止。

3. 推荐媒体架构

保留现有分段 TTS 作为生成和缓存最小单元，再由持久化 worker 用 FFmpeg 合成为一个版本化整篇 MP3。 浏览器只持有一个长期存在的 HTMLAudioElement，并对单文件使用原生循环，避免依赖后台 JavaScript 切换段落。

segment TTS cache → missing segments generated independently → explicit silence inserted between segments → FFmpeg decode/concat/re-encode → ffprobe actual duration → global segment/sentence timeline → atomic publish of one article MP3

4. 整篇资产版本

缓存键必须覆盖所有会改变声音或时间轴的输入：

article_id + ordered(segment_id, TTS text hash, segment asset id) + resolved default voice + speed = 1.0 + pause policy version + encoder profile version + timeline version

正文、顺序、语言或读音修正变化后，新旧资产不会误命中。

5. 持久任务与失败处理

  • 任务状态写入 PostgreSQL，不再使用进程内 job 字典。
  • worker 采用租约、心跳、崩溃恢复与每段独立重试。
  • 任一段最终失败则整篇 job 失败，展示失败段并提供一键重试。
  • 不发布半成品，不静默跳段；重试只补缺失或失败段。
  • 准备过程允许站内切页，迷你播放器持续展示进度。

6. 数据模型

  • article_tts_jobs：用户、文章、输入哈希、状态、总段数、完成数、失败段、错误码、重试、租约与时间戳。
  • article_tts_assets：文章、输入哈希、音色、速度、停顿/编码版本、媒体路径、时长、大小、时间轴与状态。
  • article_tts_asset_segments：整篇资产与各分段资产的关系、顺序、全局起止时间和文本哈希。
  • 本机恢复状态不新增服务端表：保存 asset_id + article_id + position_ms + updated_at，24 小时过期。

7. API 契约

POST /articles/{article_id}/full-tts-jobs GET /full-tts-jobs/{job_id} GET /articles/{article_id}/full-tts GET /media/tts/articles/{asset_id}
  • 创建接口幂等；缓存命中直接返回完成资产。
  • 状态接口返回段进度、失败段、文件大小、时长和最终时间轴。
  • 媒体接口必须按资产归属验证当前用户，不能只验证“已登录”。

8. 后端与部署

  • API 镜像安装 FFmpeg/ffprobe。
  • 新增生产 worker，与 API 共享 TTS 媒体卷。
  • MVP 可用 PostgreSQL claim job，无需立即引入 Redis。
  • 临时文件完成后原子重命名；增加磁盘配额、TTL 与孤儿资产清理。
  • edge-tts 从 7.2.7 升级到 7.2.8，并回归跨 chunk 时间轴。

9. 前端全局播放器

播放器从练习页 Hook 提升到应用根层 Provider/store，跨站内路由存在。

idle → preparing → ready → downloading → playing ↔ paused ↘ failed ↘ stale ↘ sleep-expired
  • 练习页和文章列表均可启动；全局迷你播放器显示准备、下载、播放、暂停、失效和错误状态。
  • 音档就绪后只提示，不自动发声；所有恢复与播放都要求用户手势。
  • 下载完整 Blob 后创建 Object URL，网络随后断开仍可完成本次播放；页面被系统回收后不承诺离线。
  • 文件超过 20 MB 时下载前确认；不依赖 iOS 不稳定的网络类型检测。
  • 设置 Media Session 元数据和 play/pause handler，作为渐进增强。

10. 恢复与定时

  • 每隔数秒节流保存精确 position_ms。
  • 联网重开 24 小时内提示恢复；用户点击后 seek 到精确秒数。
  • 资产版本变化时不把旧秒数套到新文件。
  • 睡眠定时按现实时间倒计时，暂停和系统中断期间继续。
  • 选择“本轮结束”时关闭 loop，在当前全文结束点停止。

11. 音频冲突

  • 录音、单段朗读或句子朗读开始前自动暂停整篇播放器。
  • 操作结束后保持暂停，必须由用户手动恢复。
  • 来电、Siri、闹钟、耳机断开等中断后保持暂停并提示。
  • 多标签页只允许一个播放器；后点击播放的标签页接管并暂停其他标签页。
  • 切换文章先确认，再停止当前文章并准备新文章。

12. 音频失效与手动更新

  • 文章或读音变化后，将当前整篇资产标为 stale，但正在播放的旧音档允许继续到用户停止。
  • 下一次播放前必须准备最新版本。
  • 提供“更新音频”按钮；点击后立即停止旧音档并启动新版准备。
  • 新版就绪后只显示站内 Toast/迷你播放器提示，由用户手动播放；不申请系统通知权限。

14. 核心验收标准

  • 所有现有合法文章（最多 20,000 字符）可生成一个完整 MP3；缺段时不可播放。
  • 段间和循环边界停顿符合配置；整篇时间轴与最终文件时长一致。
  • 文件完整下载后断网，当前页面存活期间仍能持续循环。
  • 精确位置恢复误差控制在 1 秒内；过期或资产变化不错误恢复。
  • 睡眠定时、录音暂停、段句朗读暂停、手动更新停止和多标签页接管均符合上述规则。
  • 最新版 iOS Safari 完成切 App、锁屏、熄屏、控制中心、蓝牙耳机和长时循环实测；结果写入兼容矩阵，不包装为原生级保证。
  • Chrome iOS 完成相同核心兼容验证后再标记兼容。

15. 明确不做

  • Capacitor/原生 iOS App。
  • 原生级后台可靠性 SLA。
  • 永久离线下载和跨设备位置同步。
  • 音色选择、变速、进度拖动和文章播放队列。
  • Web Push/系统准备完成通知。

16. 主要风险

  • iOS 仍可能冻结或回收网页进程；单音档只能降低风险，不能消除。
  • 长文章完整 Blob 会占用内存，必须通过 20k 实测决定保护阈值。
  • FFmpeg 合并、时间轴偏移和编码时长可能漂移，必须用最终文件反向校验。
  • 持久音频会增长磁盘占用，需要版本清理和配额监控。
  • 批量 TTS 可能放大供应商延迟与成本，需要 worker 并发和重试上限。
